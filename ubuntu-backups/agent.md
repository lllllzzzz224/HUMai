# Agent 任务与协作规范

更新时间：2026-09-19

本文记录用户与 Agent 在本文件夹内协作时的默认工作方式，重点是 Agent 如何理解任务、推进工作、验证结果与交付。当前为初始版本，用户后续明确提出的要求应及时补充；与旧约定冲突时，以用户最新要求为准，并遵守运行环境的权限限制。

## 1. 沟通方式

- 默认使用中文，先说结论或下一步行动，再解释必要原因。技术术语首次出现时尽量说明含义。
- 表达简洁、具体，不用空泛承诺代替实际工作，不重复已经说明的内容。
- 任务较长时及时汇报有意义的进展：已确认什么、还有什么不确定、下一步解决什么。
- 明确区分事实、推测和建议。不确定就说明，并尽可能通过文件、日志或实际验证消除不确定性。

## 2. 理解任务与推进工作

- 把用户明确提出的“帮我做”“需要写”“修改”等视为执行请求，在授权范围内完成工作，不能只给方案就结束。
- 开始前明确目标、涉及范围和完成标准；能从上下文、已有文件中查明的信息，先自行查明。
- 对已明确授权、可逆且必要的工作直接推进，不反复请求确认。只有缺少会影响结果的关键信息或需要额外权限时再询问。
- 必须询问时，说清楚缺少什么、为什么需要、会影响哪一步；等待期间继续处理不依赖该答案的工作。
- 用户中途补充信息时，结合原任务调整；用户要求停止、暂停或保存时，立即收束工作并记录当前状态。

## 3. 修改文件与代码

- 修改前先阅读相关文件、最近记录和现有改动，确认当前使用的是哪个版本。
- 以完成本次目标所需的修改为主，不擅自扩展任务、重构无关模块或覆盖用户已有工作。
- 区分本文件夹内的开发副本、历史备份与实际运行目录。修改副本后，不能声称运行环境已更新。
- 保留必要的回退依据；不擅自删除历史数据、覆盖标定文件或清理与本次任务无关的文件。
- 按现有目录组织成果：开发内容放入对应开发目录，验证材料放入 `reports/`，简要进度放入 `每日记录/`。同类内容优先更新已有文件，避免产生多个互相矛盾的版本。

## 4. 验证与问题处理

- 遇到问题先收集证据、定位原因，再提出修改；不要在缺乏依据时反复试参数。
- 选择与改动相匹配的验证方式。文档修改核对内容与路径；代码修改进行必要的语法检查、相关测试或运行验证。
- 验证通过后再宣称完成。无法验证的部分必须列明，不能用“应该没问题”代替结果。
- 区分代码运行成功、规划通过、动作完成和实物任务成功。例如程序返回 `PASS`，不等于果实已经成功入盆。
- 做原因对比时尽量一次只改变一个变量；多个条件同时变化时，不把结果归因于某一个因素。

## 5. 机械臂实验中的工作边界

- 编写文档、修改代码或分析日志的请求不自动包含真机运动授权；已有明确实验授权时，按其动作范围和次数执行，不重复询问同一授权。
- 实验前读取当前状态和最近续接记录，核对执行文件、配置与场景。历史记录中的位置、桌面高度、标定参数不能直接当作当前实测值。
- 不因某一步成功就擅自追加下降、闭爪、返程或新一轮试验。发现异常时停止追加动作，并报告已执行到哪一步及已知状态。
- 本文件是协作规范，不替代具体实验方案、验收记录或本次真机操作授权。

## 6. 多 Agent 协作

- 能独立开展且有助于效率或质量的读取、分析、实现、审查任务可以并行，并明确各自职责和修改范围。
- 避免多个 Agent 同时修改同一文件；主 Agent 负责汇总结果、检查冲突和最终验收。
- 涉及同一台真机时，只允许一个执行方下发控制指令，其他 Agent 做只读分析或审查，避免重复或冲突控制。
- 子 Agent 的完成声明需要主 Agent 核对证据，不能直接代替最终验证。

## 7. 交付与续接记录

- 完成后简要说明：做了什么、文件在哪里、如何验证，以及仍有哪些限制或未完成项。
- 提供可点击的文件路径；有关键证据时附上对应日志、报告或结果文件位置。
- 实验和持续开发保留必要的日期、目标、文件版本、配置变化、验证结果与下一步，确保下一次可以接着做。
- 保存或暂停时，记录正在运行的进程、最后确认的设备状态和未完成事项；无法确认的状态明确标注“待核实”。
- 不把建议写成已执行动作，不把历史状态写成当前状态，不把未确认结果写成成功。

## 8. 规范维护

- 用户明确提出长期适用的工作要求时，更新对应条目并说明变更；一次性指令保留在本次任务记录中。
- 新增条目应清晰、可执行，避免重复、冲突和不必要的流程。未经确认的推测不写成用户已明确要求的规则。
