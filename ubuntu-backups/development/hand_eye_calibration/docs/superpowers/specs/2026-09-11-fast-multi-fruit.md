# Fast same-class multi-fruit grasping

User-approved direction: maintain multiple targets, rank by confidence, bound planning time, exclude attempted targets automatically, and measure perception/planning/execution costs. Human removal is auxiliary; no Enter confirmation per round. Basket integration is deferred. Existing single-fruit and legacy continuous modes remain available.

Build a separate opt-in multi-fruit runner in apple_pick_v2, sharing validated return-mode geometry and physical parameters. The vision node optionally publishes timestamped complete multi-target snapshots (class, confidence, raw base-frame center, radius), deduplicated across inference tiles. Invalid/stale/partial observations must not prove the scene empty. Maintain persistent targets with one-to-one spatial association, stable fresh observations, confidence ranking, bounded retry/cooldown, and attempted-target exclusion. Do not call commanded motion physical grasp success. Refresh and revalidate targets after manual scene changes. Do not claim rigid fruit identity when associations become ambiguous.

Use a persistent node and rolling fresh snapshots instead of clearing 10-frame queues at each round boundary and again after planning. Bound candidate planning with a monotonic deadline shared across IK, collision checks, scene calls, Cartesian and OMPL requests. Timed-out planning must be cancelled/settled before another target is attempted. Cache previously useful IK preference when feasible; never reuse an executed trajectory with a mismatched start state or changed scene. Keep legacy velocity, lift and gripper settle values. This milestone need not claim a wall-time improvement until measured on hardware.

All new execution is opt-in: --execute plus --operator-confirmed; return placement only. Default is no-motion planning. Autonomous human-assisted operation requires a fresh reliable workspace-clear interlock, not fruit disappearance or a fabricated Bool publisher. Missing/false/stale interlock prevents actuation; loss during execution requests cancellation, latches fault, and does not claim stopped until confirmed. A software topic is merely an integration input, not a certified safety system. No real motion is to be run during development. Do not alter existing running ROS services.

Record high-resolution monotonic timings by perception/selection/preflight/revalidation/planning request/execution/arrival/gripper settling/interlock wait. Avoid summing inclusive and nested spans as if disjoint. Store status, target/category and attempt counts; distinguish scene empty, all targets attempted/blocked, stale perception and hardware fault. Include tests for stale/invalid/ambiguous inputs, duplicate detections, target disappearance/reappearance, timeout and interlock failures, and old-mode compatibility. Historical reports must distinguish operator waits, known temporal gates and uninstrumented intervals.

Develop in a local isolated clone containing the actual current source (including existing uncommitted changes). Only after tests/review, copy changed files back to the user-named original directory with a hash check and backup. Do not overwrite intervening user changes, historical logs or existing basin edits.
